# claude-pm: Design Notes

> Captured 2026-06-05 from a design conversation. Successor to claude-docs for team use. PM as its own repo, code repos stay code-only. To be prototyped weekend of 2026-06-06.

---

## Why a separate PM repo

claude-docs assumes embedded PM: every code repo carries its own `tasks/`, `bugs/`, `TASKS.md`, milestone files. That works for a solo developer on one or two repos. It breaks down for teams and multi-repo workstreams (nurses-station-dev, thesus-bt, Agora, Telecare Staffing DB) because:

- PM scaffolding is duplicated and drifts across repos
- No cross-project visibility, no portfolio view
- PMs, designers, and stakeholders need code access to read project state
- Templates live in N places, change in one

claude-pm moves PM to a single repo that serves all code repos. Code repos return to being code-only.

---

## Architectural shape

**PM repo = control plane.** It holds milestone stubs, statuses, assignments, the Kanban view (`BOARD.md`), and bug stubs. It does not hold task content.

**Code repo branches = work content.** Detailed milestone files, implementation steps, screenshots, bug investigation notes live on the relevant branch in the relevant code repo. The PM stub references the branch.

**The Kanban surface is what fills the gap with Jira.** Jira shows ticket state. claude-pm's Kanban shows code state: which milestone has an open branch, which has a PR in review, which is merged. That difference is the whole point.

### Stub schema (PM repo)

Each milestone is a stub file in the PM repo. The stub holds only what the board needs:

```yaml
id: 0.3.7
title: Patient vitals dashboard
status: in-progress              # backlog | ready | in-progress | review | done
assignee: don                    # null when unclaimed
branches:
  - repo: nurses-station-dev
    branch: don-060526-0.3.7-vitals
  - repo: th-api
    branch: don-060526-0.3.7-vitals-api
created: 2026-06-04
last-activity: 2026-06-05
milestone-file: don-060526-0.3.7-vitals:tasks/Milestone0.3.7.md
```

`branches` is an array from day one. A milestone spanning two repos is the common case for this stack, not the exception.

### BOARD.md

Regenerated by a `/board` skill or by the reconciliation agent. Plain markdown grouped by column. GitHub renders it. Stakeholders read it in the browser. Cheapest viable Kanban. Do not build a web UI until markdown is provably insufficient.

## The reconciliation agent

The agent is what makes this design pay off. Without it, claude-pm is GitOps Jira: same manual updates, different storage. With an agent doing the bookkeeping, developers stay in code and the board stays current automatically.

### Where it runs

GitHub Action in the PM repo:

- Webhook-triggered from each watched code repo on push, PR open, PR merge
- Scheduled fallback every 15-60 minutes for full reconciliation when webhooks drop
- Runs Claude in headless mode (`claude -p`) with a "reconcile" prompt
- Read access on code repos, write access on PM repo
- Commits with `agent:` prefix so humans can spot machine changes at a glance

Webhook plus scheduled gives both speed and resilience.

### Split deterministic from judgment

90% of reconciliation is pattern matching: branch matches milestone ID, set in-progress; PR opened against main referencing the milestone, set review. Do this without invoking the LLM. Save tokens for the 10% that needs judgment:

- Reading a PR body that says "partially addresses 0.3.7, rest in #142" and knowing not to close
- Inferring intent from a vague commit message
- Generating human-readable narrative for BOARD.md and agent commits

A cheap pre-filter that only invokes Claude when something is actually ambiguous keeps cost and latency low.

### The agent reflects, it does not decide

Closing milestones, scope changes, reassignments, marking blocked: human decisions. Two guardrails:

- Mark Done only on explicit signal: `Closes-Milestone:` trailer in a PR body, commit trailer, or human flip
- Never overwrite a recent human edit. If a human moved a milestone back to Backlog, the agent does not second-guess.

### Audit trail

Every agent commit explains the change in plain language: "Moved 0.3.7 to In Review: PR #142 opened on `feat/0.3.7-vitals`". When devs trust the board they stop double-checking. When they do not, they stop using it. Narrative in commit messages is what builds that trust.

## Commit schema: the protocol between dev and agent

The agent's reliability is bottlenecked by commit message quality. The cleaner the commits, the less the agent has to guess. The schema is the contract:

```
feat(nurses-station): add patient vitals chart

Wires the chart component to the vitals API endpoint. Implements
the third task of Milestone 0.3.7.

Milestone: 0.3.7
Task: 3
Affects: nurses-station-dev, th-api
```

- Conventional Commits prefix (widely known, low friction for devs)
- Free-form body in the middle stays human
- Git trailers at the bottom are machine-parseable with `git interpret-trailers` (no LLM needed)

### Skills to draft commit messages

The format should be invisible to developers. Dev-side Claude handles it:

- `/commit-draft`: reads staged diff, current branch, and the active milestone stub. Drafts the message in the schema. Dev reviews and pastes into GitHub Desktop. Never commits directly (consistent with the existing rule).
- `/pr-draft`: same schema, scoped to the PR description. Important because squash-merge collapses individual commit messages into the squash body, so the PR description becomes the unit of truth for closure signals.

### Backstop with CI lint

Some commits will bypass the skill ("wip", "fix"). A lint at PR time that says "These commits do not match the schema. Run `/commit-draft` to fix" closes the gap without being annoying mid-flow. Lint at PR boundary, not pre-commit. Friction at the wrong moment kills adoption.

### Free changelog falls out

Well-formed commits with milestone trailers mean `/milestone-complete` can auto-generate a clean changelog. Second payoff for the same up-front investment.

## Skills inventory (target)

PM repo control:
- `/board`: render BOARD.md from stubs, grouped by column
- `/board-refresh`: trigger reconciliation pass manually
- `/milestone-define`: create a new milestone stub
- `/milestone-claim <id>`: set assignee, move to in-progress, atomic commit
- `/milestone-release <id>`: return to ready
- `/milestone-finish <id>`: move to done (last resort if the agent missed it)

Bridge skills (run from a code repo):
- `/session-start`: now points to both a code repo and the PM repo
- `/milestone-start`: reads the assigned milestone stub from PM repo, creates local milestone file on a branch
- `/task-complete`: updates the local milestone file, optionally writes activity to the PM stub

Commit and PR helpers:
- `/commit-draft`: draft commit message in schema
- `/pr-draft`: draft PR description in schema

Bugs:
- `/bug-add`: stub in PM repo plus branch in code repo
- `/bug-status`: reads from PM repo
- `/bug-fixed`: same as milestone-finish, scoped to bugs

## Open design decisions

Calls to make consciously up front:

1. **Passive or active reconciliation first.** Ship passive (humans update PM repo at handoff points). Add active (agent reads GitHub) once the workflow is validated.
2. **Binding or advisory trailers.** Does `Closes-Milestone:` flip the column immediately (binding) or is it one signal among many (advisory). Recommend binding with a confirmation prompt on closure trailers, and watch what goes wrong in the first month.
3. **Session file location.** claude-docs puts it at `[CWD]/.claude-sessions/`. claude-pm probably wants it in the PM repo, since the PM repo is the control plane. Decide and document.
4. **Version source of truth.** Code repo `package.json` is the runtime artifact; PM repo stub has its own record. On disagreement, which wins? Recommend code repo wins; PM repo records the observed version. Add a drift detector skill.
5. **Bug artifacts.** Screenshots and repro files: PM repo (visible to triagers without checkout) or branch (closer to fix)? Recommend PM repo for screenshots, branch for code.
6. **Branch creation.** Still in code repo. Branch name recorded in the PM stub. One-way write from PM to code (PM repo never modifies code repos directly).
7. **Concurrency.** Two devs trying to claim the same milestone: PM repo is git, so last-write-wins with merge conflict. Acceptable for the team's current size. Revisit when the team grows.

## Build order (suggested)

**Week 1: stubs and BOARD.md**
- PM repo scaffold
- Stub schema and one example milestone
- `/board` skill renders BOARD.md from stubs
- Manual claim/finish flow, no agent yet (passive mode)

**Week 2: bridge skills**
- `/session-start` reads both repos
- `/milestone-start` pulls stub from PM, creates branch and milestone file in code repo
- `/task-complete` updates local file, writes activity to PM stub

**Week 3: commit schema**
- `/commit-draft` and `/pr-draft`
- CI lint in one code repo
- Validate dev ergonomics with one teammate before fanning out

**Week 4: the agent**
- GitHub Action with Claude in headless mode
- Reconciliation pass: deterministic state transitions only
- Add LLM step for narrative on agent commits
- Add LLM step for ambiguity resolution last

The validating test for the whole design: pick one code repo, run the agent for a week, see if the board stays in sync with zero manual edits. If yes, fan out. If not, find the design problem before scaling.

## Lessons from claude-docs to fold in

Three robustness items from the existing repo worth addressing in the new design:

1. **Single source of truth for docs.** Generate the README skill list from the skill files. Add a CI check that fails when docs and the file system disagree. (claude-docs has at least two drift cases today: README mentions session-save and session-resume but SkillReferenceManual's TOC skips them; README's directory tree puts tutorials in the wrong folder.)
2. **Install templates with skills.** `/project-new` in claude-docs references templates at `claude-docs/docs/MilestoneTemplate.md`, but `install.sh` only copies `skills/`. The skill only works if the user happens to have claude-docs cloned in a predictable location. Fix in claude-pm by shipping templates with the skills, or by reading them from the PM repo (which is always present in the workflow).
3. **Frontmatter on every skill.** YAML frontmatter (`description`, `argument-hint`, `allowed-tools`) is the Claude Code convention. Without it, autocomplete is heuristic and permission scoping is not declarable. Mechanical to add and pays off in discoverability.

---

## Not in scope for v1

- Real-time UI beyond markdown rendering in GitHub
- Notifications (GitHub already does this)
- Time tracking
- Velocity metrics or burndown charts
- Non-GitHub backends

Add these only after the markdown plus agent loop has been used in earnest for two months.
